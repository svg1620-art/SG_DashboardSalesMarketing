# 04 — Интеграция amoCRM и синхронизация

## Клиент amoCRM (`app/amocrm.py`)

- База: `https://{subdomain}.amocrm.ru/api/v4`, авторизация `Bearer {token}`.
- Пагинация по `_links.next`, ретраи на сетевые сбои и `429` (с ожиданием).
- Методы: `account()`, `pipelines()`, `users()`, `custom_fields()`,
  `iter_leads(pipeline_id)`, `iter_status_events(created_from)`,
  `probe_events_depth()` (диагностика реальной глубины истории).

`AMOCRM_SUBDOMAIN` принимает только имя (`mycompany`) — код вычищает схему,
`.amocrm.ru` и пробелы, если их случайно указали.

## Движок синхронизации (`app/sync.py`, `run_sync(config, full)`)

Порядок прогона:

1. **Справочники.** `managers` (из `/users`), `pipeline_statuses` (из
   `/leads/pipelines`, только целевая воронка — `mapped_stage`/`is_excluded` НЕ
   перезатираются), кастомные поля (сопоставление по имени, словарь `CF_PATTERNS`).
2. **События** `lead_status_changed` → `deal_stage_history`. Диапазон: при `full`
   — с `BACKFILL_SINCE_YEAR`, иначе от последнего успешного синка минус сутки.
3. **Сделки** `/leads?filter[pipeline_id]=...` → вычисление этапов (док. 05) →
   idempotent upsert. Собирается множество актуальных `amo_lead_id`.
4. **Сверка удалённых** (`_reconcile_deals`) — см. ниже.
5. **Справочник источников** — пересобирается из значений `deals.source`.

Фоновый поток (`run_sync_background`) с прогрессом в памяти (`PROGRESS`,
polling-эндпоинт `/admin/sync/progress`), запись результата в `sync_log`.
**Advisory-lock** (`pg_try_advisory_lock`) не даёт двум процессам
(веб-воркер + шедулер) синкать одновременно.

### Запуск

- **«Обновить сейчас»** (marketer+) — инкрементальный синк.
- **«Первичный бэкофилл»** (admin) — полная история с `BACKFILL_SINCE_YEAR`.
- **Ежедневно** — APScheduler (`scheduler.py`, час `SYNC_HOUR_UTC`, UTC).

> Инкрементальный синк тоже обходит **все** сделки воронки (`iter_leads` не
> фильтрует по дате изменения), различие с бэкофиллом — только в глубине истории
> событий. Поэтому прогон занимает несколько минут.

## Сверка удалённых/перенесённых сделок

**Проблема, которую это решает:** синк делает upsert, но `/leads?filter[pipeline_id]`
не возвращает сделки, которые **удалили** или **перенесли в другую воронку**.
Без сверки они навсегда оставались бы в БД и искажали отчётность.

**Логика (`_reconcile_deals`):** `iter_leads` отдаёт ВСЕ текущие сделки воронки
(включая закрытые win/lost — они остаются в воронке). Значит сделка, которой нет
в `seen`, — удалена или перенесена. Такие сделки и их `deal_stage_history`
удаляются из БД.

**Защита от массового удаления** (на случай сбойной/неполной выгрузки): если
`seen` пустой ИЛИ под удаление попадает >20% базы и >100 сделок — сверка
пропускается, в `sync_log` пишется предупреждение (в сообщении:
`сверка пропущена (N под удаление)`).

> Сверка НЕ трогает сделки, которые всё ещё в воронке, но просто не попали в
> чей-то ручной CSV-экспорт — API их вернёт, и они останутся. Удаляются только
> реально исчезнувшие из воронки.

## Кастомные поля

Словарь `CF_PATTERNS` в `sync.py` сопоставляет поля amoCRM по вхождению подстроки
в имя:
`source`, `client_type`, `monthly_payment`, `sum_platform`, `sum_implementation`,
`sum_courses`, `license_months`.

Если в amoCRM переименуют поля — правится этот словарь (одно место).

## Диагностика синка

- Страница **Синхронизация** (`/admin/sync`) — живой статус (вверху, обновляется
  каждые 2 сек) + журнал `sync_log`.
- Статус `running` в журнале ставится в момент старта и финализируется только по
  завершении. Если процесс прервётся (деплой/рестарт) — строка останется
  «running» (косметика). Ориентироваться на живой статус вверху страницы.
- Подробнее по разбору проблем — док. 08 (runbook).
