# 08 — Эксплуатация (runbook)

Практические сценарии сопровождения.

## Деплой новой версии

Push в отслеживаемую ветку GitHub → Railway автоматически пересобирает и
деплоит. При старте прогоняются миграции и обновляется админ. Откат — задеплоить
предыдущий коммит (Railway → Deployments → Redeploy) либо `git revert` + push.

## Запуск и контроль синхронизации

1. Войти админом → **Синхронизация** (`/admin/sync`).
2. **«Обновить сейчас»** — инкрементальный синк; **«Первичный бэкофилл»** — полная
   история (после первого деплоя или при подозрении на потерю данных).
3. **Живой статус** — вверху страницы, обновляется каждые 2 сек. Ориентируйтесь
   на него, а не на строку журнала.
4. По завершении в журнале появится строка `ok` с «Финиш» и сообщением
   `OK: сделок N, событий M, удалено (нет в amo) K, поля [...]`.

### «Строка в журнале висит `running`, «Финиш» пустой»

Строка `running` создаётся при старте и финализируется только по завершении.
Если процесс прервался (деплой/рестарт контейнера) — строка останется «running».
Это **косметика**. Проверка:
- Живой статус вверху = «Простаивает» → предыдущий прогон прерван; нажмите
  «Обновить сейчас» заново.
- Живой статус = «Идёт синхронизация …» → синк реально работает, дождитесь.

## «В отчётах есть сделки, которых нет в amoCRM»

Причина: раньше синк только добавлял/обновлял и не удалял исчезнувшие сделки.
**Исправлено** — теперь при каждом синке идёт сверка (`_reconcile_deals`, док. 04):
сделки, удалённые или перенесённые из воронки, удаляются из БД.

Действие: запустите **«Обновить сейчас»**. В сообщении журнала увидите
`удалено (нет в amo) N`. Проверить конкретный ID:
`/dashboard/deals?q=<ID>` — если пусто, сделка вычищена.

Если под удаление попало >20% базы (>100 сделок) — сработает защита, сверка
пропустится с предупреждением в журнале (`сверка пропущена (N под удаление)`).
Это признак неполной выгрузки amoCRM (лимит/сбой) — перезапустите синк.

## «Метрики не сходятся с ожиданием»

1. Проверьте фильтры (период по умолчанию — текущий месяц/год; тип клиента).
2. Помните про **когортную атрибуцию**: продажа января, закрытая в июне, лежит в
   январе (док. 05). Сравнивать нужно так же.
3. Cost-метрики требуют введённых затрат — без них «—», а не «0».
4. Средний чек/LTV зависят от заполненности поля `monthly_payment` в amoCRM.
5. Сверьте сопоставление статус→этап (`pipeline_statuses.mapped_stage`) — если в
   amoCRM добавили/переименовали статус, обновите маппинг (admin) и пересинкайте.

## «Синк падает с ошибкой amoCRM»

- Проверьте `AMOCRM_SUBDOMAIN` (только имя) и `AMOCRM_TOKEN` (не истёк ли).
- Страница **amoCRM** (`/admin/amocrm-check`) покажет `/account`, воронки и
  глубину истории.
- Текст ошибки — в журнале `sync_log` (статус `error`).

## «Кнопка AI не работает»

- Задан ли `ANTHROPIC_API_KEY` в Variables? Без него кнопка вернёт «Нейросеть не
  настроена».
- Ошибки API (лимиты, неверный ключ) отдаются в панели с текстом причины.

## Резервное копирование

Данные — в управляемом PostgreSQL Railway. Настройте бэкапы средствами Railway
(снапшоты плагина Postgres). Исторические затраты продублированы в посевных
миграциях (005/006) — при пересоздании БД восстановятся автоматически.

## Логи

- Синхронизация — таблица `sync_log` + страница `/admin/sync`.
- Приложение — стандартный вывод gunicorn (Railway → Logs).
