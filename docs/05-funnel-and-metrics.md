# 05 — Воронка и метрики

Вся математика — в `app/metrics.py`. Чистая логика вычисления этапов — в
`app/stages.py` (юнит-тестируемая).

## Модель воронки

Этапы определяются **по статусам целевой воронки**. Воронка линейная и
порядковая: достигнут этап N ⇒ пройдены все предыдущие.

| # | Этап | Определение |
|---|------|-------------|
| 1 | MQL | Все созданные сделки воронки (кроме «Дубль») |
| 2 | SQL | Заполнено поле «Тип клиента в сделке» |
| 3 | Назначено встреч | Статус «Назначена встреча» / «Не пришёл на встречу» |
| 4 | Проведено встреч | Статус «Проведена встреча» |
| 5 | Выставлено счетов | Статус «Выставлен счёт» |
| 6 | Продажи | Успешно закрыта (`is_won`, глобальный статус 142) |

**Неквал** = ушедшие в «Закрыто и не реализовано» (глобальные статусы amoCRM
142/143 win/lost) без назначенной встречи.

### Вычисление этапов (`stages.compute_stages`)

- `max_stage_reached` + булевы флаги из множества пройденных статусов (история
  событий) и текущего статуса;
- **ordinal fill**: достижение этапа N выставляет все предыдущие милестоны;
- «Дубль» (`is_excluded`) → полностью вне воронки (по решению заказчика
  исключается даже из MQL);
- `stage_source = events`, если есть история; иначе `fallback` (по текущему
  статусу).

Сопоставление статус→этап хранится в `pipeline_statuses.mapped_stage`,
редактируется admin; посев — миграция `002`.

### Типы клиента (МКК / КК / СКК)

Полное значение поля «тип клиента» (напр. «МКК (неключевой до 100)») сокращается
до короткого кода функцией `metrics.short_client_type` (берёт ведущий
буквенный токен). Варианты одного кода объединяются. Цвета —
`metrics.CLIENT_TYPE_COLORS`.

## Когортная атрибуция (ключевой принцип)

Все метрики привязаны к месяцу **создания** лида. Продажа/выручка «догоняются» в
строку месяца создания в момент закрытия сделки.

> Пример: лид создан в январе, закрыт в июне → продажа добавляется в **январь**
> (не в июнь). Так конверсия января растёт со временем на сопоставимых данных, а
> MQL/SQL июня не размываются январской выручкой.

Реализовано атрибуцией по `created_at` в `metrics._deal_where` (общий построитель
`WHERE` для всех метрик).

## Cost-метрики (по источникам)

`metrics.by_source`, `_add_derived`:
- **CPL** = затраты / MQL;
- **цена встречи** = затраты / назначено встреч;
- **цена продажи** = затраты / продажи;
- **доходимость** = проведено / назначено;
- **% неквала** = неквал / MQL;
- **ROAS** = выручка / затраты;
- **средний чек (источник)** = выручка / продажи.

Cost-метрики требуют введённых затрат (`costs_touches`). Без затрат показывается
**«—»**, а не «0 ₽» (иначе вводит в заблуждение).

Источники без единого результата дальше лида и без выручки скрываются из таблицы;
строка «Все источники» учитывает всё.

## Юнит-экономика по месяцам

`metrics.by_month`, `_add_unit_economics`. Сверено с исходным листом «Воронка по
месяцам (скрипт)» — цифры сходятся.

- **CAC** = (Расходы на маркетинг + Расходы на продажи) ÷ число продаж месяца.
  Значения берутся прямыми тоталами из `monthly_costs`. «Расходы на маркетинг»
  уже включают рекламу и ЗП маркетинга; «Расходы на продажи» — ЗП продаж и налоги.
  Реклама из «Затрат и касаний» в CAC повторно НЕ добавляется.
- **Средний чек** = средний ежемесячный платёж на клиента (`monthly_payment`).
- **LTV** = средний чек × `LTV_MONTHS` (по умолчанию 21).
- **LTV:CAC** — на одного клиента.
- **Длина сделки** = среднее число календарных месяцев от создания до закрытия
  включительно (январь→июнь = 6).

Поэтапные конверсии между соседними этапами (MQL→SQL, SQL→встреча, доходимость,
встреча→счёт, счёт→продажа, MQL→продажа) считаются для каждого месяца; на
дашборде подсвечивается динамика к соседнему столбцу (▲зелёный/▼красный).

## Разрезы по типам клиента и менеджерам

- **Карточки по типам клиента за период** (`client_type_cards`): кол-во,
  конверсия MQL→успех, длина сделки + дельта к предыдущему периоду той же длины
  (`_shift_period`).
- **Стек-воронка по типу клиента** (`_funnel_by_client_type`): с этапа SQL, доли
  типов внутри этапа.
- **Конверсия по типам клиента по месяцам** (`_ct_conversion_by_month`): линия
  на каждый тип.
- **По менеджерам** (`by_manager`, `manager_cards`): только количественные
  метрики и конверсии. **Cost-метрики в разрезе менеджеров не считаются** —
  затраты привязаны к источнику, а не к менеджеру (ограничение методики ТЗ §4).
