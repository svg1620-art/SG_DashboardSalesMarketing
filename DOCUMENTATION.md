# DashboardSales&Marketing — документация для разработчиков

Веб-платформа аналитики воронки продаж: миграция с Google Sheets + amoCRM на
самостоятельный сервис (Flask + PostgreSQL + Railway) с прямой интеграцией к
amoCRM API. **Источник правды — база данных**, а не ячейки таблицы.

> Рабочее название продукта: **DashboardSales&Marketing** (в исходном ТЗ
> фигурировало как «SG_FunnelBoard»).

## 1. Обзор и стек

| Слой | Технология |
|------|------------|
| Backend | Flask 3 + Jinja2, gunicorn |
| БД | PostgreSQL (Railway managed), `psycopg2-binary` (пул соединений) |
| Планировщик | APScheduler (ежедневный синк) |
| HTTP к amoCRM | `httpx` (пагинация, ретраи, обработка 429) |
| Графики | Chart.js (вендорится локально в `static/vendor/`) |
| Экспорт | `openpyxl` (генерация в память) |
| Нейросеть | `anthropic` SDK, модель `claude-opus-4-8` |
| Деплой | Railway (nixpacks), GitHub |

Архитектурные принципы:
- **Источник правды — БД.** amoCRM синкается в PostgreSQL; дашборды считают
  метрики SQL-агрегацией на лету.
- **Идемпотентность синка** — upsert по `amo_lead_id`, повторный запуск не
  плодит дубли.
- **ФС Railway эфемерна** — ничего не пишем на диск; экспорт генерится в память.
- **Когортная атрибуция** — метрики привязаны к месяцу *создания* лида и
  «догоняются» по мере закрытия сделок (см. §10).

## 3. Локальный запуск

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env          # заполнить DATABASE_URL, amoCRM, ключи
python scripts/migrate.py --create-admin
python wsgi.py                # http://localhost:8000
```

`scripts/migrate.py`:
- без флагов — применяет непринятые миграции (учёт в таблице `schema_migrations`);
- `--create-admin` — дополнительно создаёт/обновляет админа из
  `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD` (idempotent, `ON CONFLICT`).

## 5. Деплой на Railway

1. New Project → Deploy from GitHub repo → выбрать репозиторий и ветку.
2. Добавить **PostgreSQL** (регион **EU** по ТЗ — задаётся при создании,
   потом не меняется).
3. У сервиса `web` в **Variables** задать переменные из §4
   (`DATABASE_URL = ${{Postgres.DATABASE_URL}}`).
4. Старт-команда (`railway.json`) при деплое:
   `python scripts/migrate.py --create-admin && gunicorn wsgi:app ...`
   — миграции + создание админа + запуск.

Первичная загрузка данных: войти админом → **Синхронизация** →
«Первичный бэкофилл» (тянет все сделки Воронки1 с 2023 г. и события).

## 6. Миграции и схема БД

Миграции — SQL-файлы в `migrations/`, применяются по порядку имени, учёт в
`schema_migrations`. Добавление новой миграции: создать файл `007_*.sql`, при
следующем деплое применится автоматически.

| Файл | Содержимое |
|------|------------|
| `001_initial_schema.sql` | Все таблицы ТЗ §8 |
| `002_stage_mapping_seed.sql` | Флаг `is_excluded` + посев сопоставления статусов «Воронки1» |
| `003_monthly_costs.sql` | Таблица `monthly_costs` (ранняя версия) |
| `004_monthly_costs_totals.sql` | Переход `monthly_costs` на прямые тоталы `cost_marketing`/`cost_sales` |
| `005_seed_monthly_costs.sql` | Посев исторических месячных затрат из таблицы заказчика |
| `006_seed_costs_touches.sql` | Посев рекламы по месяц×источник из «Затраты и касания» |

### Таблицы

- **`app_users`** — `id, email, password_hash, role (admin/marketer/viewer), is_active, created_at`.
- **`pipeline_statuses`** — `status_id, pipeline_id, name, sort_order, mapped_stage, is_excluded`.
  `mapped_stage ∈ {mql, sql, meeting_scheduled, meeting_held, invoiced, won, lost, none}`.
- **`managers`** — `amo_user_id (PK), name, is_active`.
- **`sources`** — `id, name (uniq), is_active`. Формируется объединением источников из сделок.
- **`deals`** — `amo_lead_id (PK), pipeline_id, current_status_id, responsible_user_id,
  source, price, created_at, closed_at, is_won, is_lost, client_type, monthly_payment,
  sum_platform, sum_implementation, sum_manager, sum_courses, license_months,
  max_stage_reached, reached_mql/reached_sql/meeting_scheduled/meeting_held/invoiced/sold (bool),
  stage_source (events/fallback), synced_at, raw (jsonb)`.
- **`deal_stage_history`** — `id, amo_lead_id, status_id, mapped_stage, changed_at`
  (uniq по `amo_lead_id, status_id, changed_at`).
- **`costs_touches`** — `id, period_month (date), source, amount, touches, comment,
  created_by, created_at, updated_at` (uniq по `period_month, source`).
- **`monthly_costs`** — `period_month (PK), cost_marketing, cost_sales, comment, created_by, updated_at`.
- **`sync_log`** — `id, started_at, finished_at, deals_synced, events_synced, status (ok/error/running), message`.

## 7. Аутентификация и роли

- **Пароли** — PBKDF2-HMAC-SHA256, соль на пользователя, 200k итераций
  (`auth.hash_password` / `verify_password`). Формат:
  `pbkdf2_sha256$200000$<salt_hex>$<hash_hex>`.
- **Сессии** — Flask signed cookies. `load_current_user` в `before_request`
  кладёт `g.user` (или `None`).
- **Роли** (по возрастанию прав): `viewer (0) < marketer (1) < admin (2)`.
  Декораторы: `@login_required`, `@role_required("marketer")`.

| Роль | Права |
|------|-------|
| **admin** | Всё + управление пользователями + запуск синхронизации |
| **marketer** | Просмотр дашбордов, ввод «Затраты и касания», «Обновить сейчас», экспорт |
| **viewer** | Только просмотр и экспорт |

Регистрация закрыта: пользователей заводит admin в `/admin/users`
(создание, смена роли/пароля, активация, удаление; защита от самоблокировки).

## 8. Интеграция с amoCRM и синхронизация

**Клиент** (`amocrm.py`): база `https://{subdomain}.amocrm.ru/api/v4`, авторизация
`Bearer {token}`. Пагинация по `_links.next`, ретраи (сетевые сбои, 429).
Методы: `account()`, `pipelines()`, `users()`, `custom_fields()`,
`iter_leads(pipeline_id)`, `iter_status_events(created_from)`,
`probe_events_depth()` (проверка глубины истории).

**Движок** (`sync.py`, `run_sync(config, full)`):
1. Справочники: `managers` (из `/users`), `pipeline_statuses` (из `/leads/pipelines`,
   только целевая воронка; `mapped_stage`/`is_excluded` НЕ перезатираются —
   правки admin и посев миграции сохраняются), кастомные поля (сопоставление по
   имени, `CF_PATTERNS`).
2. События `lead_status_changed` → `deal_stage_history` (с какой даты — при `full`
   с `BACKFILL_SINCE_YEAR`, иначе от последнего успешного синка − сутки).
3. Сделки `/leads?filter[pipeline_id]=...` → вычисление этапов (§9) → upsert.
4. Обновление справочника `sources`.

**Сверка удалённых/перенесённых** (`_reconcile_deals`): `iter_leads` отдаёт все
текущие сделки воронки (включая закрытые), поэтому сделка, отсутствующая в
выгрузке, — это удалённая или перенесённая в другую воронку. Такие сделки (и их
историю) удаляем из БД, чтобы не влияли на отчёты. Защита: при пустой или
подозрительно малой выгрузке (>20% базы и >100 сделок под удаление) сверка
пропускается, в `sync_log` пишется предупреждение.

Фоновый поток с прогрессом (`PROGRESS`, polling-эндпоинт `/admin/sync/progress`),
запись в `sync_log`. **Advisory-lock** (`pg_try_advisory_lock`) не даёт двум
воркерам/шедулеру синкать одновременно.

Запуск: кнопка «Обновить сейчас» (marketer+), «Бэкофилл» (admin), ежедневно
через APScheduler (`scheduler.py`, час `SYNC_HOUR_UTC`).

**Кастомные поля** (`CF_PATTERNS` в `sync.py`) сопоставляются по вхождению в имя:
`source`, `client_type`, `monthly_payment`, `sum_platform`, `sum_implementation`,
`sum_courses`, `license_months`. Если имена в amoCRM изменятся — правится этот словарь.

## 9. Модель воронки и вычисление этапов

Этапы определяются **по статусам «Воронки1»**, воронка линейная и порядковая:
достигнутый этап N ⇒ пройдены все предыдущие.

| # | Этап | Определение |
|---|------|-------------|
| 1 | MQL | Все созданные сделки Воронки1 (кроме «Дубль») |
| 2 | SQL | Заполнено поле «Тип клиента в сделке» |
| 3 | Назначено встреч | Статус «Назначена встреча» / «Не пришёл на встречу» |
| 4 | Проведено встреч | Статус «Проведена встреча» |
| 5 | Выставлено счетов | Статус «Выставлен счёт» |
| 6 | Продажи | Успешно закрыта (`is_won`, статус 142) |

**Неквал** = ушедшие в «Закрыто и не реализовано» (142/143 — глобальные статусы
amoCRM won/lost) без назначенной встречи.

**Вычисление** (`stages.compute_stages`, чистая функция):
- `max_stage_reached` + булевы флаги из множества пройденных статусов
  (история событий) + текущего статуса;
- ordinal fill: достижение этапа N выставляет все предыдущие милестоны;
- «Дубль» (`is_excluded`) → полностью вне воронки (решение по MQL: исключается);
- `stage_source = events` если есть история, иначе `fallback` (по текущему статусу).

Сопоставление статус→этап хранится в `pipeline_statuses.mapped_stage`,
редактируется admin; посев — миграция `002`. Короткие коды типов клиента
(МКК/КК/СКК) вычисляются `metrics.short_client_type` из полного значения поля.

## 10. Методика метрик и юнит-экономики

**Когортная атрибуция (ключевой принцип).** Все метрики привязаны к месяцу
**создания** лида. Продажа/выручка «догоняются» в строку месяца создания в
момент закрытия. Пример: лид января, закрытый в июне, добавляет продажу в
январь. Так конверсия месяца растёт со временем на сопоставимых данных, а
MQL/SQL июня не размываются январской выручкой. Реализовано атрибуцией по
`created_at` в `metrics._deal_where`.

**Поэтапные конверсии, цены, доходимость** (`metrics.by_source`, `_add_derived`):
- CPL = затраты / MQL; цена встречи = затраты / назначено; цена продажи = затраты / продажи;
- доходимость = проведено / назначено; % неквала = неквал / MQL; ROAS = выручка / затраты;
- cost-метрики требуют введённых затрат — без них показывается «—», а не «0 ₽».

**Юнит-экономика по месяцам** (`metrics.by_month`, `_add_unit_economics`), сверено
с исходным листом «Воронка по месяцам (скрипт)»:
- **CAC** = (Расходы на маркетинг + Расходы на продажи) ÷ число продаж месяца.
  «Расходы на маркетинг» уже включают рекламу (из «Затрат и касаний») и ЗП
  маркетинга; «Расходы на продажи» — ЗП продаж и налоги. Значения берутся
  прямыми тоталами из `monthly_costs` (реклама не задваивается).
- **Средний чек** = средний ежемесячный платёж на клиента (`monthly_payment`).
- **LTV** = средний чек × `LTV_MONTHS` (по умолчанию 21).
- **LTV:CAC** — на одного клиента.
- **Длина сделки** = среднее число календарных месяцев от создания до закрытия
  (включительно: январь→июнь = 6).

**Дельты к прошлому периоду** (`metrics.client_type_cards`) — сравнение с
предыдущим отрезком той же длины (`_shift_period`), относительное изменение.

**Разрез по менеджерам** (`metrics.by_manager`) — только количественные метрики и
конверсии (cost-метрики не считаются: затраты привязаны к источнику, не к
менеджеру — ограничение методики ТЗ §4).

## 11. Дашборды и вкладки

Единая **панель фильтров** (`_filters.html`): период (с/по), менеджер, источник,
тип клиента, воронка (пока «Воронка1»). Фильтры применяются к вкладке и переносятся
по ссылкам. При открытии подставляется период по умолчанию (редирект с датами в
URL): дашборды — текущий месяц, «По месяцам» — текущий год.

| Вкладка | Маршрут | Содержимое |
|---------|---------|------------|
| По источникам | `/dashboard/sources` | Таблица метрик по источникам + «Все источники»; воронка Chart.js с разбивкой по типу клиента (с этапа SQL). Пустые источники скрыты. |
| По месяцам | `/dashboard/months` | Транспонированная матрица (месяцы — колонки, метрики — строки) с подсветкой динамики конверсий (▲зелёный/▼красный); карточки по типам клиента с дельтами; диаграммы MQL→SQL/SQL→успех и конверсия по типам клиента; сравнение месяцев («месяц года» / multiselect). |
| По менеджерам | `/dashboard/managers` | Карточки по типам клиента (конверсия + длина сделки) + сводная таблица. |
| Затраты и касания | `/dashboard/costs` | Ввод рекламы по источникам и месячных затрат (marketer+). |
| Сделки | `/dashboard/deals` | Плоская таблица с поиском (ID/источник/тип) и пагинацией. |
| Экспорт | `/dashboard/export` | Кнопка выгрузки в Excel. |

Основной модуль расчётов — `metrics.py`. Форматирование чисел — Jinja-фильтры в
`__init__.py`: `num`, `money`, `pct`, `ratio`, `dur`, `ctshort`.

## 12. Ввод затрат

Вкладка **«Затраты и касания»** (`/dashboard/costs`), ввод — роли marketer/admin,
viewer только просмотр:
- **Реклама по источникам** → `costs_touches` (месяц × источник × сумма × касания × комментарий). Upsert по (месяц, источник).
- **Затраты по месяцам** → `monthly_costs` (Расходы на маркетинг, Расходы на продажи). Upsert по месяцу.

Правки поверх посеянных миграцией данных сохраняются (миграции применяются один раз).

## 13. Экспорт в Excel

`export.py` (openpyxl, генерация в память). Кнопка «⬇ Excel» в панели фильтров
каждого дашборда (выгружает текущий вид) + вкладка «Экспорт». Листы: По источникам,
По месяцам, По менеджерам, Сделки, Реклама (затраты), Затраты по месяцам. Учитывает
активные фильтры; значения без формул, форматы (проценты `0.0%`, суммы `#,##0 ₽`).

## 14. Нейросеть (анализ по запросу)

`ai.py` — кнопка «Рекомендации от нейросети» на «По источникам/месяцам/менеджерам».
**Только по запросу**, не автоматически. По клику собираются агрегированные метрики
разреза (с учётом фильтров), передаются модели `claude-opus-4-8` (официальный SDK
`anthropic`, adaptive thinking + effort medium). Ответ — разделы «Закономерности»,
«Аномалии», «Рекомендации» (безопасный Markdown→HTML рендер). Эндпоинт
`POST /ai/recommendations?page=...`. Без `ANTHROPIC_API_KEY` — понятная ошибка.

Системный промпт и сбор данных — в `ai.py` (`SYSTEM_PROMPT`, `gather_data`).

## 16. Как расширять

- **Новая метрика** — добавить в `metrics.py` (SQL-агрегация по `deals` +
  `costs_touches`/`monthly_costs` с `_deal_where`), пробросить в шаблон.
- **Новое поле из amoCRM** — добавить паттерн в `CF_PATTERNS` (`sync.py`),
  извлечение в `_build_deal_row`, колонку в `deals` (миграция).
- **Изменить сопоставление статусов** — через UI (admin) или посев миграцией;
  синк не перезатирает `mapped_stage`/`is_excluded`.
- **Новая вкладка** — добавить в `TABS` (`dashboard_bp.py`), маршрут, шаблон.
- **Миграция** — новый файл `NNN_*.sql` в `migrations/` (применяется по порядку).
- **Фирменный стиль** — палитра и компоненты в `static/css/style.css`
  (тёмная база `#0A0A0D`, синий `#1467F5`, циан `#00BFDC`, Manrope + JetBrains Mono).

## 17. Тестирование

Проект проверялся на локальном PostgreSQL (см. историю коммитов): миграции,
идемпотентность синка, вычисление этапов (юнит-тесты `stages.compute_stages`),
метрики (сверка с исходной таблицей — CAC/LTV/LTV:CAC сходятся до рубля), CRUD
затрат и пользователей, ролевой доступ, экспорт, AI-эндпоинт (с мок-моделью).

Рекомендация для команды: вынести проверки в `pytest` + фикстуру временной БД,
покрыть `stages.py` (чистая логика) и `metrics.py` (агрегации на посеянных данных).
